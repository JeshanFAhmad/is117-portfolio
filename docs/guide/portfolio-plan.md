## Project proposal

**Working idea:** Course FAQ assistant using a small set of public course documents or sample data.

**Problem:** A student may need to locate information spread across several course documents.

**Possible first version:**
1. Load a small collection of public or instructor-provided sample documents.
2. Let a user enter a question.
3. Return a concise answer with the supporting document or section.
4. If the source does not contain the answer, say that the information was not found.
5. Include a small test set to check answer accuracy and unsupported questions.

**Evidence to publish:** A short demo, source code, setup instructions, test cases, screenshots if useful, and a discussion of limitations. Do not upload private class materials, personal data, API keys, or copyrighted course content without permission.

## Skills to develop

- **Gap 1 — Applied AI and evaluation:** Practice connecting an application to an AI service or retrieval approach, then test outputs systematically.
- **Gap 2 — APIs and deployment:** Practice using an API, handling errors, documenting setup, and publishing a small application.

These are starting hypotheses based on the two example postings. Update them after reviewing more current job descriptions and comparing their actual requirements with completed coursework and projects.

## One-week next step

- **Day 1:** Choose a small public or sample document set and define the FAQ assistant's user problem.
- **Day 2:** Sketch the user flow and list the minimum features.
- **Day 3:** Build a basic interface or working prototype.
- **Day 4:** Connect the document lookup or AI feature.
- **Day 5:** Create test questions, including questions the system should not answer.
- **Day 6:** Ask a classmate to try the prototype and review the instructions.
- **Day 7:** Record feedback, make one improvement, and commit the change with a clear message.

## Feedback and decision history

Use GitHub issues for peer feedback. For each issue, record:

1. **Observation:** What specific part of the project needs attention?
2. **Why it matters:** How does it affect clarity, accuracy, usability, or evidence?
3. **Decision:** Implement, investigate, defer, or decline—with a reason.
4. **Change:** Link the documentation or code commit/PR and mention the issue number in the commit message.
5. **Verification:** Explain what was checked and ask the reviewer to retry the change before closing a resolved issue.

Keep unfinished items open with a concrete next step. Do not close an issue simply because a change was committed.
